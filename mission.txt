Continuously improve Voice Journal while I am asleep. Treat this as a production software-maintenance and improvement shift, not a code-generation exercise.

PRIMARY OBJECTIVE:
Every run, inspect the current state of the repository and deployed application, identify the highest-value improvements, implement them, validate them, deploy them, and verify that the deployed application actually works.

DO NOT wait for me to provide tasks. Proactively find useful work.

==================================================
PHASE 1 — UNDERSTAND THE CURRENT SYSTEM

1. Pull the latest state of the repository.
2. Inspect the complete project structure before making changes.
3. Read the README, configuration, package/dependency files, CI/CD configuration, tests, deployment configuration, and important application code.
4. Determine:
    * application architecture
    * frontend/backend architecture
    * speech-to-text/transcription pipeline
    * transcript storage and processing
    * APIs
    * authentication
    * database/data model
    * deployment architecture
    * test infrastructure
    * observability/logging
    * current known limitations
5. Review recent commits and previous work so you do not duplicate or undo existing improvements.

==================================================
PHASE 2 — TRANSCRIPT QUALITY AUDIT

Treat transcript quality as a first-class product metric.

Inspect the application’s transcription pipeline and evaluate:

* transcription accuracy
* punctuation
* capitalization
* sentence segmentation
* speaker/voice handling if applicable
* timestamps if applicable
* filler-word handling
* repeated-word handling
* hallucinated words
* missing words
* malformed transcripts
* partial transcripts
* long-recording behavior
* short-recording behavior
* noisy-audio behavior
* silence handling
* microphone/input failures
* language handling
* latency
* transcription cost/efficiency
* failure recovery
* edge cases

Use any real transcript fixtures, test audio, sample data, logs, or evaluation tooling already available in the repository.

Do not claim transcript quality is good merely because the code looks reasonable. Measure it wherever possible.

Build or improve automated transcript-quality tests when useful.

When improving transcription, preserve the user’s original meaning. Do not silently rewrite personal journal content in a way that changes meaning.

==================================================
PHASE 3 — FIND IMPROVEMENTS

Prioritize work in this order:

1. Production bugs and broken functionality
2. Data-loss or reliability risks
3. Security vulnerabilities
4. Incorrect transcription behavior
5. User-facing UX problems
6. Performance bottlenecks
7. Reliability and error handling
8. Test coverage and regression prevention
9. Maintainability and code quality
10. Accessibility
11. Developer experience
12. Sensible product improvements

Look for both obvious and non-obvious problems.

Do not invent features merely to generate commits.

==================================================
PHASE 4 — IMPLEMENT

For each selected improvement:

1. Understand the existing implementation.
2. Make the smallest robust change that solves the actual problem.
3. Keep the architecture coherent.
4. Avoid unnecessary rewrites.
5. Preserve existing working behavior.
6. Add or update tests.
7. Update documentation when behavior changes.
8. Keep secrets, credentials, tokens, personal data, and private journal content out of source control and logs.

Prefer several logically isolated improvements over one enormous unreviewable change.

==================================================
PHASE 5 — TEST AGGRESSIVELY

After every meaningful change:

1. Run the project’s existing test suite.
2. Run linting/type checks/static analysis where applicable.
3. Run the build.
4. Run relevant unit/integration/e2e tests.
5. Test important error paths.
6. Test regression cases related to the change.
7. Test transcription behavior using available fixtures.
8. Fix failures rather than ignoring them.

Do not mark a task complete merely because the application builds.

A successful build is NOT equivalent to a working application.

==================================================
PHASE 6 — SECURITY AND PRIVACY

Before deployment, inspect for:

* leaked secrets
* exposed API keys
* insecure environment handling
* authorization mistakes
* unsafe user input
* injection vulnerabilities
* insecure endpoints
* accidental journal-data exposure
* sensitive data in logs
* excessive permissions
* unsafe file handling

Voice Journal contains potentially private personal journal data. Treat all journal/transcript/audio content as sensitive.

Never expose private journal content in logs, commits, reports, issues, or notifications.

==================================================
PHASE 7 — DEPLOY

When changes are validated:

1. Commit logically related changes.
2. Push to the appropriate branch.
3. Trigger or perform the repository’s normal deployment process.
4. Wait for deployment completion.
5. Check deployment/CI status.
6. Verify the production deployment.

Do NOT assume deployment succeeded because a command returned successfully.

==================================================
PHASE 8 — PRODUCTION VERIFICATION

After deployment, perform real smoke tests against the deployed application.

Verify at minimum, where applicable:

* application loads
* authentication works
* recording starts
* microphone/input handling works
* recording stops correctly
* audio is processed
* transcription completes
* transcript is displayed correctly
* transcript is stored correctly
* journal entry creation works
* existing entries still load
* editing works
* deletion behavior remains correct
* error states are handled correctly
* no console/runtime errors are introduced
* important API endpoints respond correctly
* performance is acceptable

If something fails:

DO NOT STOP.

Diagnose the failure, fix it, redeploy, and test again.

Repeat this cycle:

IMPLEMENT → TEST → DEPLOY → VERIFY → DIAGNOSE → FIX → REDEPLOY

until the release is genuinely stable.

==================================================
PHASE 9 — ITERATIVE AUTONOMOUS LOOP

Do not stop after fixing the first bug.

After each successful improvement:

1. Re-evaluate the application.
2. Find the next highest-value issue.
3. Implement it.
4. Test it.
5. Deploy it.
6. Verify it.

Continue this loop for the remainder of the scheduled work window.

The purpose of every nightly run is to leave the repository measurably better than it was at the beginning of the run.

==================================================
COMMIT POLICY

Target up to 20 meaningful commits per nightly run.

IMPORTANT:

Never create fake, cosmetic, trivial, duplicate, meaningless, or artificially fragmented commits solely to reach 20.

A commit counts only when it represents a genuine engineering change with a clear purpose and validation.

Examples of legitimate commits:

* fix transcription bug
* improve transcript normalization
* add regression test
* improve recording reliability
* optimize API performance
* improve error handling
* fix UI issue
* improve accessibility
* improve deployment reliability
* improve logging/observability without exposing private data
* refactor code when it produces a concrete maintainability benefit
* add meaningful test coverage
* improve security
* improve database/query performance
* improve deployment configuration

If only 4 meaningful improvements exist, make 4 commits.

Quality is more important than the numerical target.

Never manufacture work.

==================================================
NO DESTRUCTIVE ENGINEERING

Do NOT:

* delete working functionality without a strong reason
* rewrite the entire application unnecessarily
* replace stable architecture merely because another approach is fashionable
* remove tests to make them pass
* weaken validation
* disable security controls
* suppress errors instead of fixing them
* expose journal/transcript/audio data
* commit secrets
* modify production databases destructively without a safe migration strategy
* introduce speculative features without evidence of benefit

Before any potentially destructive change, create a safe rollback point and prefer reversible changes.

==================================================
GIT DISCIPLINE

Use clear commit messages.

Each commit should answer:

WHAT changed?
WHY did it change?
HOW was it validated?

Keep unrelated changes in separate commits.

Do not rewrite public history or force-push main unless absolutely necessary and explicitly permitted by the repository’s workflow.

==================================================
DEFINITION OF DONE

A nightly improvement is complete only when:

* implementation is complete
* tests pass
* build passes
* lint/type checks pass where applicable
* deployment succeeds
* production smoke tests pass
* the original problem is actually resolved
* no obvious regression was introduced

Do not report “fixed” when you merely changed code.
